# 2단계: 구축 (Construction)

프로젝트 정의 단계에서 정의된 개발 유닛을 테스트되고 운영 준비가 완료된 코드로 변환합니다. [도메인 주도 설계 (Domain-Driven Design)](https://ko.wikipedia.org/wiki/%EB%8F%84%EB%A9%94%EC%9D%B8_%EC%A3%BC%EB%8F%84_%EC%84%A4%EA%B3%84)  원칙을 적용하여 도메인 설계부터 시작하고, 이를 바탕으로 코드를 생성합니다.

---

**구축 단계의 스테이지**

구축 단계는 다음 순서로 진행됩니다:

| 순서 | 스테이지 | 설명 | 실행 조건 | 주요 산출물 |
| --- | --- | --- | --- | --- |
| 1 | **Functional Design** | 기술 독립적 비즈니스 로직 설계 | 조건부 (유닛별) | `domain-entities.md`, `business-rules.md` |
| 2 | **NFR Requirements** | 비기능 요구사항 및 기술 스택 선택 | 조건부 (유닛별) | `nfr-requirements.md`, `tech-stack-decisions.md` |
| 3 | **NFR Design** | NFR 패턴과 논리적 컴포넌트 정의 | 조건부 (유닛별) | `nfr-design-patterns.md`, `logical-components.md` |
| 4 | **Infrastructure Design** | 논리적 컴포넌트를 인프라에 매핑 | 조건부 (유닛별) | `infrastructure-design.md`, `deployment-architecture.md` |
| 5 | **Code Planning** | 코드 생성 상세 계획 수립 | 항상 | `code-generation-plan.md` |
| 6 | **Code Generation** | 계획에 따라 실제 코드 생성 | 항상 | `src/`, `tests/` 코드 |
| 7 | **Build and Test** | 빌드 및 포괄적 테스트 실행 | 항상 | `build-instructions.md`, test 결과 |

---

**유닛별 설계 프로세스**

각 개발 유닛은 복잡도에 따라 필요한 설계 단계를 거칩니다. 간단한 유닛은 설계를 건너뛰고 바로 코드 생성으로 진행할 수 있습니다.

**1. Functional Design (기능 설계)**

**목적**: 기술과 독립적으로 비즈니스 로직을 설계합니다.

**수행 내용**:

- 도메인 엔티티 정의 (속성, 행동, 불변 조건)
- 비즈니스 규칙 명세 (언제, 무엇을, 어떻게)
- 비즈니스 로직 모델 (엔티티 간 상호작용)

**산출물**:

- `domain-entities.md` - 엔티티 정의
- `business-rules.md` - 비즈니스 규칙
- `business-logic-model.md` - 로직 흐름

**언제 실행**: 새로운 비즈니스 로직이 필요한 경우

---

**2. NFR Requirements (비기능 요구사항)**

**목적**: 성능, 보안, 확장성 등 품질 속성을 정의하고 기술 스택을 선택합니다.

**수행 내용**:

- 성능 요구사항 정의 (응답 시간, 처리량, 리소스 제한)
- 보안 요구사항 정의 (인증, 암호화, 접근 제어)
- 확장성 요구사항 정의 (동시 사용자, 데이터 증가)
- 기술 스택 선택 및 근거 문서화

**산출물**:

- `nfr-requirements.md` - 비기능 요구사항
- `tech-stack-decisions.md` - 기술 스택 결정 및 근거

**언제 실행**: 새로운 기술 스택 선택이 필요하거나 NFR이 중요한 경우

---

**3. NFR Design (NFR 설계)**

**목적**: NFR을 충족하기 위한 구체적인 설계 패턴과 컴포넌트를 정의합니다.

**수행 내용**:

- 성능 최적화 패턴 선택 (캐싱, 배칭, 비동기 처리)
- 보안 패턴 적용 (인증, 권한, 암호화)
- 복원력 패턴 적용 (재시도, 서킷 브레이커, 폴백)
- 논리적 컴포넌트 정의 (역할과 책임)

**산출물**:

- `nfr-design-patterns.md` - 적용할 설계 패턴
- `logical-components.md` - 논리적 컴포넌트 구조

**언제 실행**: NFR이 복잡하거나 특정 패턴 적용이 필요한 경우

---

**4. Infrastructure Design (인프라 설계)**

**목적**: 논리적 컴포넌트를 실제 클라우드 서비스에 매핑합니다.

**수행 내용**:

- 컴퓨팅 리소스 선택 (EC2, Lambda, ECS, Fargate)
- 스토리지 선택 (S3, RDS, DynamoDB, ElastiCache)
- 네트워킹 설계 (VPC, 로드 밸런서, API Gateway)
- 배포 전략 수립 (Blue/Green, Canary, Rolling)
- 비용 추정 및 최적화

**산출물**:

- `infrastructure-design.md` - 인프라 아키텍처
- `deployment-architecture.md` - 배포 구조 및 전략

**언제 실행**: 클라우드 배포가 필요한 경우

---

**코드 생성 및 검증**

**Code Planning (코드 계획)**

**목적**: 무엇을 어떤 순서로 생성할지 상세 계획을 수립합니다.

**수행 내용**:

- 생성할 파일 목록 작성
- 파일 간 의존성 순서 결정
- 각 파일의 역할과 책임 정의
- 스토리와 파일 매핑

**산출물**: `code-generation-plan.md`

---

**Code Generation (코드 생성)**

**목적**: 계획에 따라 실제 코드를 생성합니다.

**수행 내용**:

- 계획의 각 단계를 순서대로 실행
- 도메인 모델을 코드로 변환
- 비즈니스 규칙을 로직으로 구현
- 테스트 코드 자동 생성
- 진행 상황을 체크박스로 추적

**생성 위치**:

- 실제 코드: workspace root (`src/`, `tests/`)
- 코드 문서: `aidlc-docs/construction/`

---

**Build and Test (빌드 및 테스트)**

**목적**: 생성된 코드를 빌드하고 포괄적으로 테스트합니다.

**수행 내용**:

- 모든 유닛 빌드 및 의존성 해결
- 단위 테스트 실행 (각 클래스/함수)
- 통합 테스트 실행 (유닛 간 상호작용)
- 성능 테스트 실행 (NFR 충족 검증)
- 보안 스캔 실행 (취약점 검사)
- 테스트 커버리지 분석

**산출물**:

- `build-instructions.md` - 빌드 방법
- `test-instructions.md` - 테스트 실행 방법
- `test-results.md` - 테스트 결과 및 커버리지

---

**손쉬운 유지보수와 빠른 반복**

AI-DLC의 큰 장점은 **변경과 개선이 쉽다**는 것입니다.

**변경 요청이 생기면**

**테스트에서 발견된 이슈**

`"로그인 시 에러 처리가 부족합니다"
→ AI에게 요청 → 에러 처리 추가 → 테스트 → 확인`

**새로운 요구사항**

`"비밀번호 재설정 기능이 필요합니다"
→ AI에게 요청 → 설계 → 코드 생성 → 테스트 → 확인`

**성능 개선**

`"응답 시간이 느립니다"
→ AI에게 요청 → 원인 분석 → 최적화 → 테스트 → 확인`

**여러분의 역할**

AI가 변경사항을 빠르게 구현하면, 여러분은:

- ✅ 변경 내용 검토
- ✅ 비즈니스 요구사항 충족 확인
- ✅ 품질 기준 만족 확인
- ✅ 승인 및 배포 결정

**빠른 반복의 이점**

**시간 단축**: 몇 시간~며칠 단위로 변경사항 반영

**품질 유지**: 매번 테스트와 검증을 거쳐 품질 보장

**문서 동기화**: 코드 변경 시 관련 문서도 자동 업데이트

**추적 가능**: 모든 변경 이력이 Git과 문서에 기록
