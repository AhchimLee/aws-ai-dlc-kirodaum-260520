# PR/FAQ: 테이블오더 서비스 — "OrderEasy"

---

## Press Release

### 제목

**OrderEasy — 소규모 매장도 장애에 강한 디지털 주문 시스템을 즉시 도입할 수 있습니다**

### 부제

QR코드 스캔 또는 테이블 태블릿으로 고객이 직접 주문하고, 매장 운영자는 실시간으로 주문을 관리하는 클라우드 네이티브 테이블오더 플랫폼

### 날짜

2025년 5월

### 요약

OrderEasy는 음식점, 카페 등 소규모 매장을 위한 테이블오더 서비스입니다. 고객은 테이블에 비치된 QR코드를 스캔하거나 태블릿을 통해 메뉴를 조회하고 직접 주문할 수 있습니다. 매장 운영자는 실시간 대시보드에서 주문 상태를 모니터링하고, 메뉴와 테이블을 관리할 수 있습니다.

OrderEasy는 단순한 주문 앱이 아닙니다. 중복 주문 방지, 결제 장애 격리, 구조화된 로그 추적, 무중단 배포 등 엔터프라이즈 수준의 운영 안정성을 갖춘 시스템입니다. AWS EKS(Kubernetes) 환경에서 즉시 운영 가능한 Product Ready 아키텍처를 기반으로 설계되었습니다.

---

### 문제 정의

소규모 매장에서 디지털 주문 시스템을 도입할 때 다음과 같은 문제가 반복적으로 발생합니다.

**고객 관점의 문제:**

- 주문 버튼을 여러 번 눌러 중복 주문이 발생한다.
- 결제 시스템 장애 시 주문이 완료되었는지 알 수 없다.
- 직원을 호출해야 하는 대기 시간이 길다.

**매장 운영자 관점의 문제:**

- 주문이 누락되거나 중복 처리되어 고객 불만이 발생한다.
- 장애 발생 시 어떤 주문이 실패했는지 추적할 수 없다.
- 피크 시간대에 주문 폭주로 시스템이 불안정해진다.

**운영/개발 관점의 문제:**

- 로컬 개발 환경에서는 드러나지 않는 운영 환경 장애 시나리오가 존재한다.
- 배포 중 트래픽 유실이 발생한다.
- 장애 원인 추적에 과도한 시간이 소요된다.

---

### 솔루션

OrderEasy는 이러한 문제를 다음과 같이 해결합니다.

**중복 주문 완전 차단:**
모든 주문 요청에 Idempotency Key를 적용하여, 네트워크 재시도나 중복 클릭으로 인한 중복 주문을 원천 차단합니다. 동일 키로 재요청 시 기존 결과를 반환하거나 409 Conflict로 안전하게 차단합니다.

**결제 장애 격리:**
외부 결제 API 장애가 전체 시스템으로 전파되지 않도록 Circuit Breaker 패턴을 적용합니다. 결제 타임아웃 발생 시 주문 상태를 안전하게 격리하고, 운영자가 원인을 추적할 수 있는 구조화된 로그를 남깁니다.

**실시간 주문 관리:**
Server-Sent Events(SSE) 기반으로 2초 이내에 신규 주문이 관리자 대시보드에 표시됩니다. 테이블별 그리드 레이아웃으로 매장 전체 상황을 한눈에 파악할 수 있습니다.

**무중단 운영:**
Kubernetes Graceful Shutdown을 구현하여 배포나 노드 교체 시에도 진행 중인 요청이 안전하게 완료됩니다. Health Check(Liveness/Readiness Probe)로 트래픽 유실을 방지합니다.

**완전한 장애 추적:**
모든 요청에 trace_id와 correlation_id를 부여하고, 주문 생성부터 결제 처리까지 전체 흐름을 stdout JSON 로그로 추적할 수 있습니다.

### 시작하기

1. 매장 관리자가 OrderEasy에 매장을 등록합니다.
2. 메뉴와 카테고리를 설정합니다.
3. 각 테이블에 태블릿을 설치하고 테이블 번호를 등록합니다.
4. 고객은 태블릿에서 바로 메뉴를 조회하고 주문합니다.
5. 관리자는 실시간 대시보드에서 주문을 확인하고 상태를 관리합니다.

### 아키텍처 개요

OrderEasy는 Hexagonal Architecture (Ports and Adapters) 패턴을 채택합니다.

- **Domain Layer**: 외부 기술에 의존하지 않는 순수 비즈니스 로직 (Order, Payment, Table, MenuItem 엔티티)
- **Application Layer**: Use Case 단위 비즈니스 흐름, Port 인터페이스에 의존
- **Infrastructure Layer**: DB, Payment Gateway, Redis 등 외부 시스템 Adapter

이 구조를 통해 비즈니스 로직과 외부 기술 의존성을 명확히 분리하고, 외부 장애가 Domain Layer로 전파되지 않도록 합니다.

## FAQ

### 고객 관련 FAQ

**Q1. 고객이 주문하려면 앱을 설치해야 하나요?**

아닙니다. OrderEasy는 웹 기반으로 동작합니다. 고객은 테이블에 비치된 태블릿에서 브라우저를 통해 바로 메뉴를 조회하고 주문할 수 있습니다. 별도의 앱 설치나 회원가입이 필요하지 않습니다.

**Q2. 고객이 주문 버튼을 여러 번 누르면 어떻게 되나요?**

모든 주문 요청에는 고유한 Idempotency Key가 부여됩니다. 동일한 키로 중복 요청이 들어오면 시스템이 이를 감지하여 중복 주문을 생성하지 않습니다. 첫 번째 요청이 처리 중이면 409 Conflict를 반환하고, 이미 완료되었으면 기존 결과를 반환합니다.

**Q3. 이전 손님의 주문 내역이 다음 손님에게 보이나요?**

아닙니다. 테이블 세션 개념을 적용하여, 관리자가 "이용 완료" 처리를 하면 해당 세션의 주문 내역은 과거 이력으로 이동합니다. 새로운 고객은 깨끗한 상태에서 주문을 시작합니다.

**Q4. 주문 후 상태를 확인할 수 있나요?**

네. 고객은 주문 내역 화면에서 현재 세션의 모든 주문 상태(대기중/준비중/완료)를 확인할 수 있습니다.

### 매장 운영자 관련 FAQ

**Q5. 매장 관리자는 어떻게 로그인하나요?**

매장 식별자, 사용자명, 비밀번호로 로그인합니다. JWT 토큰 기반 인증으로 16시간 동안 세션이 유지되며, 브라우저를 새로고침해도 로그아웃되지 않습니다.

**Q6. 주문이 들어오면 어떻게 알 수 있나요?**

Server-Sent Events(SSE) 기반 실시간 통신으로, 신규 주문이 2초 이내에 관리자 대시보드에 표시됩니다. 신규 주문은 시각적으로 강조(색상 변경, 애니메이션)되어 즉시 인지할 수 있습니다.

**Q7. 잘못된 주문을 삭제할 수 있나요?**

네. 관리자는 특정 주문을 삭제할 수 있습니다. 삭제 시 확인 팝업이 표시되며, 삭제 후 해당 테이블의 총 주문액이 자동으로 재계산됩니다.

**Q8. 메뉴를 실시간으로 변경할 수 있나요?**

네. 관리자 화면에서 메뉴 등록, 수정, 삭제, 노출 순서 조정이 가능합니다. 변경 사항은 고객 화면에 즉시 반영됩니다.

### 기술/운영 관련 FAQ

**Q9. 결제 시스템 장애가 발생하면 어떻게 되나요?**

외부 결제 API에 3000ms 타임아웃을 적용하고, Circuit Breaker 패턴으로 장애를 격리합니다. 실패율 50% 초과 또는 응답 시간 3000ms 초과가 5회 연속 발생하면 Circuit이 Open되어 추가 호출을 차단합니다. 이때 주문 상태는 Pending 또는 Failed로 안전하게 격리되며, CRITICAL 레벨의 구조화 로그가 출력됩니다.

**Q10. 서버 배포 중에 주문이 유실되나요?**

아닙니다. Kubernetes Graceful Shutdown을 구현하여, SIGTERM 수신 시 Readiness Probe가 즉시 실패하여 신규 트래픽 유입을 차단하고, 진행 중인 요청은 설정된 유예 기간 내에 안전하게 완료됩니다.

**Q11. 장애 발생 시 원인을 어떻게 추적하나요?**

모든 요청에 trace_id와 correlation_id가 부여되며, API Layer부터 Repository Layer까지 전체 계층에 전파됩니다. stdout 기반 Structured JSON Logging으로 OpenSearch, CloudWatch, Fluent Bit 등에서 파싱 가능한 형태로 로그가 출력됩니다. 단일 trace_id로 주문 생성부터 결제 처리까지 전체 흐름을 추적할 수 있습니다.

**Q12. 동시에 많은 주문이 들어와도 안정적인가요?**

테이블 단위 Rate Limiting(분당 10회)으로 악성 요청과 중복 클릭을 방지합니다. Stateless Architecture로 설계되어 수평 확장이 가능하며, Kubernetes 환경에서 트래픽에 따라 자동 스케일링됩니다.

**Q13. 실제 결제 연동이 포함되어 있나요?**

MVP 단계에서는 실제 PG사 연동은 포함하지 않습니다. 결제 흐름의 아키텍처(타임아웃, Circuit Breaker, 멱등성)는 완전히 구현하되, 외부 결제 API는 Mock으로 대체합니다. 이를 통해 장애 시나리오 검증과 운영 안정성 테스트가 가능합니다.

**Q14. 어떤 기술 스택을 사용하나요?**

- **아키텍처**: Hexagonal Architecture (Ports and Adapters) — Domain, Application, Infrastructure 계층 분리
- **런타임**: AWS EKS (Kubernetes) 배포 전제 설계
- **로깅**: stdout 기반 Structured JSON Logging (OpenSearch/CloudWatch/Fluent Bit 파싱 가능)
- **인증**: JWT 토큰 기반 (bcrypt 비밀번호 해싱)
- **실시간 통신**: Server-Sent Events (SSE)
- **장애 대응**: Circuit Breaker, Timeout (3000ms), Retry with Exponential Backoff
- **데이터 무결성**: Idempotency Key (DB 기반, 확장 시 Redis), Rate Limiting (Token Bucket)
- **운영**: Graceful Shutdown, Liveness/Readiness Probe, Stateless Architecture
- **테스트**: pytest 기반, Edge Case 필수 (10개 이상 시나리오)
- **설정**: 환경 변수 기반 (하드코딩 금지)

**Q15. 보안은 어떻게 보장하나요?**

Security by Default 원칙을 적용합니다. 입력값 검증, SQL Injection 방지, 비밀번호 bcrypt 해싱, Secret 하드코딩 금지, 에러 응답에서 내부 정보 노출 금지, 로그에 개인정보/Secret 출력 금지 등의 보안 통제를 기본 설계에 포함합니다. 모든 설정값은 환경 변수 또는 Config Mapping으로 주입합니다.

### 비즈니스 관련 FAQ

**Q16. 이 서비스의 차별점은 무엇인가요?**

대부분의 테이블오더 솔루션은 "정상 흐름"만 고려합니다. OrderEasy는 "실패 흐름"을 통제합니다. 중복 주문 방지, 결제 장애 격리, 무중단 배포, 완전한 장애 추적 등 엔터프라이즈 수준의 운영 안정성을 소규모 매장에도 제공합니다.

**Q17. MVP에서 제외되는 기능은 무엇인가요?**

다음 기능은 MVP 범위에서 제외됩니다:

- 실제 PG사 결제 연동
- 푸시/SMS/이메일 알림
- 주방 디스플레이 시스템(KDS)
- 배달 플랫폼 연동
- POS 시스템 연동
- 다국어 지원
- 데이터 분석 대시보드
- 재고 관리
- 예약 시스템

**Q18. 향후 확장 계획은 무엇인가요?**

MVP 검증 후 다음 단계로 확장을 계획합니다:

1. **Phase 2**: 실제 PG 연동, Redis 기반 Idempotency Store, 관리자 대시보드 고도화
2. **Phase 3**: 주방 디스플레이 연동, 푸시 알림, 매출 리포트
3. **Phase 4**: 멀티테넌트 SaaS 전환, 다국어 지원, 배달 플랫폼 연동

### AI-DLC 프로세스 관련 FAQ

**Q19. AI-DLC를 어떻게 활용하나요?**

AI-DLC(AI-Driven Development Life Cycle)를 통해 요구사항 정의, 아키텍처 설계, 구현, 테스트, 운영 검증까지 전 과정을 추적 가능한 방식으로 수행합니다. AI가 생성한 코드를 무조건 승인하지 않고, Human Approval Gate를 통해 품질을 통제합니다.

**Q20. AI가 생성한 코드의 품질을 어떻게 보장하나요?**

다음 검증 절차를 거칩니다:

- Hardcoded Secret 탐지
- SQL Injection 위험 검증
- Race Condition 가능성 검증
- Transaction Boundary 검증
- Domain/Infrastructure 분리 검증
- Edge Case 테스트 (중복 주문, 결제 타임아웃, DB 타임아웃, Graceful Shutdown 등)
- Architecture Decision Record(ADR) 작성
- Operational Readiness Review

검증 없이 구현 완료 처리를 하지 않으며, 모든 주요 결정은 audit.md에 기록됩니다.
